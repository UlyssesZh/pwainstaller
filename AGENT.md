# PWA Installer

A native Kotlin Android app (`io.github.ulysseszh.pwainstaller`) that builds, signs, exports, and installs independent APKs backed by the system WebView. Both the installer and generated apps support Android API 21+, target API 37, and compile to Java 11 bytecode.

## Build

Install a JDK compatible with Gradle (17 or newer), Android SDK platform 37, and build tools 36.0.0. Set `ANDROID_HOME` or put your SDK path in an untracked `local.properties`:

```properties
sdk.dir=/path/to/Android/Sdk
```

```sh
./gradlew :app:assembleDebug
./gradlew :core:test :app:testDebugUnitTest :app:lintDebug
```

The installer APK is `app/build/outputs/apk/debug/app-debug.apk`. Gradle automatically builds both unsigned runtime templates and embeds them as assets; no Android SDK, compiler, or network build service is needed on the phone. Release builds use `./gradlew :app:assembleRelease` and need your own installer signing configuration before distribution. Keep the installer certificate stable: generated apps pin it for profile access.

With a running emulator or connected device:

```sh
./gradlew :app:connectedDebugAndroidTest
```

Device tests serve a local fixture website on the device. They exercise authenticated manifest discovery, persistent metadata and atomic imports, APK generation and installation, independent WebView execution, unauthorized package/certificate access, and cookie/localStorage/IndexedDB migration. They temporarily install and remove only the `io.github.ulysseszh.pwainstaller.integration*` test packages.

## Use

Tap **+**, enter the website URL, and save. The installer discovers `<link rel="manifest">`, downloads metadata and icons, and asks Android to install the generated APK. Website, manifest, and icon fetching shows a Material loading dialog with the current stage and download percentage when the server supplies a content length; transfers without one use an indeterminate progress bar. App-list manifest refreshes use the same interface. Expand **Advanced settings** to supply a manifest URL, custom HTTP headers, package name, manual manifest, or disable installation. Authentication failures and pages without a manifest link offer a temporary WebView browser; a missing manifest also offers adding without a manifest. Manual creation uses the page title when the name is blank. Tap the temporary browser’s check mark to return to the form and continue editing before fetching or saving. The new-app Advanced settings also have a button to open it manually. The first opening for a new draft starts with clean browsing data; reopening it in that draft continues the same session. Installing directly from that editor imports its cookies, localStorage, IndexedDB, and other browsing data into the generated app. Saving metadata without installing retains the temporary profile privately for the next installation. Pending installations retain a private profile backup across retries; browsing data is excluded from metadata. The temporary browser uses a Material toolbar, outlined address field, loading progress, and themed authentication and permission dialogs, with light/dark mode and dynamic colors. Its toolbar provides back, refresh, and the check mark for finishing sign-in. HTTP Basic sign-in is also supported, with session credentials restricted to the authenticated origin and realm.

Choose **List** or **Tiles** in Settings; both layouts sort apps alphabetically by name using the current locale and have no item outlines. Tap an item to launch its app. In list mode, use the menu button or long press; in tiles mode, only long press opens the menu. The menu offers reinstall, manifest refresh, editing, a temporary browser, deletion with optional uninstall, system app info, browsing-data import/export, and APK export. This temporary browser starts with the installed app’s browsing data and asks before importing its changes back; cancellation preserves the installed profile. Failed imports retain a private recovery copy for retry. Missing packages appear gray. The toolbar menu imports/exports the library, opens **Settings** and About, and offers **Reinstall all**. Reinstall all processes saved apps in sequence and retains its queue across installation confirmations and interruptions. The **Continue** floating button above **+** appears only for interrupted work or a paused reinstall queue and resumes it. APK building and installation sequencing run in a foreground service while you use the installer or another app. The service submits completed APKs, restores browsing data and advances Reinstall all even when the app activity is closed. Authorized unfinished builds can resume when Android restarts the service. A bounded, renewed partial wake lock covers active processing and is released while waiting for user confirmation or when work finishes. Installation confirmation notifications open the recovery prompt when Android cannot show the installer from the background. Each list item immediately shows its queued/building status and progress, with tile progress overlaid on its icon; finished operations leave no status. Build phases distinguish metadata validation, signing-key loading, filter processing, template reading, icon preparation, resource packaging, and signing, and progress notifications open the app list. Settings lets you choose 1–16 parallel APK builders, defaulting to two on devices with multiple processors and one otherwise. Changes apply immediately: raising the limit starts queued work; lowering it lets existing builds finish. Reinstall all prepares up to the selected number of apps ahead of installation confirmations. Additional work queues, while installation confirmations remain sequential. Each operation has one progress notification, kept through installation and confirmation until completion or failure. Progress reporting runs independently of slow installation or data-transfer work. Unchanged notifications are not reposted; changing progress shares a bounded update rate fairly across concurrent builders. Completion removes all build notifications, including the foreground placeholder. Completed background and silent installations show the app-named success toast from the completion pipeline; opening the app later does not repeat that toast. The determinate build indicator advances through fixed phase ranges from empty to full, including signing; it does not restart at each phase. Status survives screen recreation. The item menu includes **View build logs** for the last build, including diagnostics and failure details; build-error dialogs link to the same log. Opening logs during a build follows its current output, preserves text selection, and supports copying the whole log with a toolbar button. Scrolling up pauses automatic scrolling; returning to the bottom resumes following new entries.

Use the checkmark in the editor’s top bar to save when adding or editing an app; there is no footer Save button. Editing keeps the manifest URL independent from the fetched metadata. Saving validates and stores the current metadata and cached/uploaded icons locally, then builds the APK if installation is enabled; it never downloads pages, manifests, icons, shortcut icons, or filter lists. Fetching the manifest in an existing app requires confirmation before replacing fields and downloaded icons; Cancel keeps unsaved edits. Use **Fetch manifest** or **Refresh default rules** explicitly to update downloaded content. Fetching is explicit, and the “Use a web app manifest” checkbox appears only when creating an app. Theme and background colors use a color picker with a saturation/brightness plane, HSV/RGB/opacity sliders, and editable CSS hex values (including shorthand and an optional final alpha byte). The controls stay synchronized and invalid hex input must be corrected before applying a color. Display mode and orientation use selection menus. Upload multiple PNG, JPEG, WebP, or SVG icons, or use **Fetch online icons** to enter an image or webpage URL. The popup starts with the current start/base URL, uses the fetch headers and user agent, and adds the resulting icons. Its lookup URL is not saved in metadata. The images retain their resolutions and work together; there is no exclusive icon selection. Each icon has independent `any`, `maskable`, and `monochrome` purpose checkboxes, including combinations. Manifest purposes are read when fetching. SVG icons are labeled **Scalable (SVG)** and use `sizes: "any"`; the PNG preview dimensions are not treated as their intrinsic size. Their original SVG bytes survive metadata export/import, are packaged in generated apps, and are rasterized at each required Android launcher size. Older downloaded SVGs retain their cached preview until an explicit manifest fetch restores the source; previously uploaded SVGs need re-uploading to recover their original artwork. The full manifest editor shows ordinary slashes in URLs and paths. Standard fields have individual controls; **Edit full manifest JSON** preserves and edits every additional manifest member. Apply JSON to populate the individual controls; saving combines those controls with the JSON. Changing an installed package name offers migration. Installation, profile import, and removal occur in that order; The system package installer confirms each installation; Shizuku can install silently. Uninstallation uses the selected installation method too; Shizuku can remove apps silently once permission is granted.

The launcher’s **Add web app** shortcut opens the new-app form, and **Reinstall all** starts the same batch flow as the list menu (Android 7.1+). Sharing an HTTP or HTTPS URL to PWA Installer also opens that form with the base URL filled in. Advanced settings include an optional user agent, applied to the installed WebView, manifest/icon fetching, and the temporary sign-in browser, plus an opt-in WebView content debugging setting. Android development builds can force WebView debugging on regardless of that setting. **Use notch areas** is enabled by default for each web app, including existing records that lack this option. It lets the app use display-cutout areas while respecting visible system bars and the keyboard; turn it off to keep content within cutout-safe bounds. Both the window mode and content insets are set, so opting out also works with Android 15’s enforced edge-to-edge layout. Save and reinstall to apply the option to an installed app.

When editing an existing app, all settings are shown directly; there is no Advanced toggle or base URL field. Change its start URL in the manifest fields. Toolbar and system Back ask before discarding unsaved changes; returning every value to its initial state leaves without a prompt. If a pending operation blocks opening the editor, its explanation stays visible until acknowledged or dismissed and survives screen recreation. Saving existing metadata does not fetch web content.

When adding an app without a manifest, page discovery also fills unset regular and dark theme colors from valid `theme-color` meta tags, including `prefers-color-scheme` light/dark queries. It uses the first matching tag for each scheme and reuses the page fetched for title/icon discovery. Explicit color choices are preserved. Media conditions requiring unknown viewport/device information are skipped.

App URL scopes and patterns in the app settings determine which top-level URLs stay in the app. Enter multiple URLs, one per line; matching any entry keeps the content in the app. An ordinary scope URL such as `https://example.com/app/` includes its descendants on the same origin. The editor has one **App URL scopes and patterns** control. Fetching or applying a manifest replaces these entries with its resolved `scope` (or its default scope); additional scopes can then be entered. The standard manifest metadata still contains a single `scope` URL. Default scopes for a bare registrable domain also include its `www` counterpart, keeping the same scheme, port, and path; existing subdomains and explicit custom scopes are not broadened. Leave the control empty to use these defaults for the base URL. For HTTP(S) URLs outside these scopes, the app checks HTTP redirects in the background with its user agent and cookies before handing the destination to Android. Redirects returning to an app scope stay in the app; destinations still outside its scopes use Android’s normal URL associations, including installed apps and browser defaults. The calling web app is excluded when it would otherwise handle its own out-of-scope link again. This also applies to popups. Only HTTP redirect responses are followed; HTTP 200 pages are handed off without inspecting HTML refresh tags or running redirect scripts. A site can return HTTP 200 to the web app’s user agent while returning a redirect to curl. Wildcard patterns can also be used, for example `https://example.com/app/*` or `https://*.example.com/*`; `*` matches any scheme, host, port, or path where supplied. A port omitted from a pattern means the scheme’s default port. These navigation rules do not block page subresources. The temporary browser permits navigation across sites for sign-in.

A reinstall with a different signing key offers uninstall/reinstall recovery. The installer first exports and validates a private browsing-data backup. Removal uses the selected system or Shizuku method, then installation proceeds and the backup is restored. Failed backups leave the installed package intact; proceeding without data requires a separate confirmation. Backups survive installation/restore failures and process restarts and are removed only after a successful restore. **Continue** resumes recovery.

**Settings** includes installation, library layout, adblock, and signing options. Installation method and layout changes apply immediately. Tiles use the manifest short name (falling back to the full name), the same 48 dp icons as list view, and compact spacing. List view shows full names. Filter URLs apply automatically after a short typing pause, and update intervals apply when selected; leaving Settings also applies valid pending edits. Invalid URLs show an inline error and retain the last valid configuration. There are no Save buttons in Settings. Keystore import asks before replacing the current key; a validated upload saves automatically. If validation fails, correcting its credentials retries the pending import without changing the active key. The default installation method uses Android’s system package installer. Shizuku installation requires Android 7.0+, a running Shizuku service (version 13+), and an explicit permission grant. Selecting Shizuku in Settings applies the method and immediately requests its permission when needed. If Shizuku is not running, the app explains that it must be started; select Shizuku again after starting it to authorize. Once authorized, it installs without a package-installer confirmation. Signature conflicts still use the same backup and uninstall recovery flow.

Global adblock settings accept one AdGuard filter URL per line. Lines beginning with `#` are disabled and retained in settings and backups. The default configuration is refreshed weekly:

```text
# https://filters.adtidy.org/android/filters/2_optimized.txt
https://filters.adtidy.org/android/filters/18.txt
https://filters.adtidy.org/android/filters/20.txt
```

Cookie Notices and Mobile App Banners are enabled; the base filter is available but commented out. Choose manual, daily, weekly, or monthly updates, or refresh immediately. Android schedules automatic downloads subject to network availability and background-work constraints. Initial downloads and scheduled updates run in the background, or can be requested with the refresh button. Creating an app uses available cached rules and never waits for filter-list downloads. Automatic rule suggestions are debounced while entering a URL and run separately from web fetching. If no lists have been downloaded yet, refresh the global lists in Settings and then refresh the app’s defaults to add them.

Each web app stores its own editable rule snapshot (expand **Edit adblock rules** to view or change it; large snapshots use small editable pages), initially selected from the global lists for its base URL. Updating global lists never changes saved or installed apps. **Refresh default rules** in the editor selects rules for the current start URL as a new snapshot from the current global cache without downloading filter lists. Selection avoids compiling URL matchers and reuses the last host’s result while its source lists are unchanged. Tapping Save during refresh shows a notice and waits for the refreshed snapshot; refresh the global lists in Settings first to download newer rules, then save and reinstall the web app to apply them. Network blocking, exceptions, cosmetic CSS, ExtendedCSS, and recognized AdGuard scriptlets are supported. Unsupported network transformations, arbitrary JavaScript rules, and HTML response rewriting are skipped. WebView request information limits resource-type classification, and old WebViews apply page scripts after navigation begins.

English and Simplified Chinese resources are included. Material 3 follows the device's light/dark mode and uses dynamic colors where supported.

**Settings → Manage user scripts and styles** maintains separate JavaScript and CSS libraries. Import a local UTF-8 file or fetch an HTTP(S) URL; files can be renamed, refreshed from their URL, or deleted. Select enabled files in each web app’s settings, save, and reinstall. Saving copies the selected files into that app’s metadata; exports, imports, and APK generation retain those copies and need no source-file downloads. Updating or deleting a library file does not change saved or installed apps. Saving an app again uses the current library versions of its selected files; imported files absent from the library remain available in that app’s selection.

User JavaScript runs once when each main document’s DOM is ready, in the page context, with a separate function scope and error handling for each file. CSS is inserted into that document; embedded frames are excluded. These are plain JavaScript/CSS files, without userscript-manager APIs such as `GM_*` or interpretation of userscript metadata headers. CSS resource URLs resolve relative to the page and remain subject to its loading policy. Modern WebViews can use constructed stylesheets if the page blocks inline styles; older WebViews can restrict user styles through the page’s content security policy. Files are limited to 1 MiB each, with at most 64 selected files and 8 MiB of serialized content per app. Large selections use chunked database storage separately from icons and manifest metadata.

Filter compilation reports percentage progress in the app list, notification, and build log. Compiled assets are cached by the complete rule snapshot and installer/compiler version; reinstalls and apps sharing identical rules can reuse them. Corrupt entries are rebuilt. The cache keeps at most 64 entries within 64 MiB and is safe to clear with the installer’s cache. Large cosmetic-rule compilations use two workers on multicore devices, preserving rule order. See [filter selection and compilation measurements](docs/rule-selection-benchmarks.md).

Generated apps retain their WebView through window-size, screen-layout, and display-density changes, so freeform resizing preserves the current document, form values, and scroll position. Changes to the active display’s identity, dimensions or density request fresh insets and layout and reattach the same WebView to its parent and briefly change its native size to encourage Chromium to recreate a stale compositor attachment and viewport. Refresh-rate, HDR and brightness changes with unchanged display geometry, as well as unrelated displays being added, do not reattach the WebView; this avoids repeatedly tearing down video surfaces. Fullscreen media uses an opaque overlay while keeping the underlying document visible with its existing viewport insets, preserving feed scroll position across fullscreen transitions. On fullscreen exit, the original document’s scroll offset is restored when the page has not navigated. Physical external-display reconnection recovery is verified on a Pixel 9 running Android 17 with Vanadium 157; the provider compatibility limits are described below. Reinstall existing generated apps to receive runtime changes.

Filter-list downloads started in Settings and scheduled updates use the same WorkManager jobs. Repeated manual requests join an already-pending update. Downloads show a notification with the current list and overall byte progress when its length is known, or indeterminate progress otherwise; they continue after Settings closes. Tapping the notification opens Settings, where the job status is also shown. These notifications are separate from the proposed web Notifications API.

## Implementation

- `app`: Kotlin activities, private SQLite metadata database, authenticated manifest fetching, APK construction, signing-key management, Storage Access Framework transfers, and a persistent install/migration journal.
- `runtime`: separately compiled Kotlin APK template, WebView launcher, and certificate-pinned profile provider. Generated APKs always have version `1.0.0` / code `1`.
- `runtime-ui`: optional runtime template containing the Material browser toolbar; apps with browser UI disabled use `runtime` without these UI libraries.
- `browser`: common Kotlin WebView browser with navigation, popups, uploads, downloads, media fullscreen, and origin-confirmed camera/microphone/location permissions. TLS validation stays with the system. No JavaScript-to-native bridge is exposed.
- `core`: Kotlin code for package identity, compiled-manifest string-pool rebuilding, and validated profile archives.

Library reads use cached names, URLs, and small icon thumbnails rather than parsing every app’s full metadata. Existing databases backfill that cache in the background. Opening the editor loads its record once and prepares previews on a dedicated worker. After any creation-time fetching and migration decision, Save returns to the app list while cached default-rule selection, validation, metadata persistence, temporary-browser data export, installation preparation, and APK generation run as a background job. New apps appear in the list before persistence finishes; saving and building share the progress indicator, notification, and log. Validation failures offer **Edit web app** to restore the submitted values. Temporary browsing data handed to a queued save is archived before another temporary browser can clear it. Signing-key settings and validated identities are cached and warmed separately. Pending operations keep large metadata snapshots separate from their small status headers, so list refreshes do not repeatedly parse filter rules or icons.

The manifest string pool is rebuilt with stable indices; arbitrary-length Unicode labels and package names are supported. The runtime template uses R8 to remove unused code. Generated APKs compress DEX, XML, and text assets while leaving PNG images and the resource table stored and aligned to four bytes. Only the scriptlet implementations and filtering helpers needed by an app are included; entire global filter downloads stay in the installer. Device tests check that a minimal generated APK remains below 400 KiB; actual size depends on icons, metadata, shortcuts, and filter helpers. A selected keystore signs every generated APK with v1 and v2 signatures. JVM tests verify the resulting APK using Android's `apksig` verifier. The build adapts the signer's non-inherited ASN.1 annotation lookup to `getAnnotation`, available on API 21, and uses Bouncy Castle's `jdk15to18` distribution for older Android cryptography APIs.

Manifest IDs resolve against the start URL's origin, and fragments are excluded from identity. Start URLs, scope, and IDs obey same-origin constraints. Relative icon and shortcut URLs resolve against the manifest URL. Fetching follows redirects with timeouts and size limits; custom headers are confined to the base origin and HTTPS downgrades are rejected. Cookies are selected for each destination URL.

Generated apps have an icon/background splash screen, including the Android 12+ system launch screen. Both the installer and generated apps support round and other launcher masks. Generated APKs include five launcher densities, choosing the smallest adequate icon for each density and retaining every original image as an asset. General-purpose artwork is padded; maskable artwork is preferred for adaptive icons with its safe zone fitted to Android’s. A supplied monochrome icon becomes the Android 13+ themed-icon layer. Older round-icon launchers have a separate circular fallback. The runtime applies the name, start URL, scope links, orientation, display/display_override, text direction, and background/theme colors.

Freeform resizing and external-display changes retain the live page. Reconnection refreshes WebView’s activity-context display observers even when Android does not send a configuration change. Display lookup prefers the activity's current valid display, with the attached hierarchy as a fallback. WebViews detach before a context observer changes their display, so Chromium can remove its density observer from the previous display. If the renderer still uses the wrong density, an optional Chromium compatibility bridge refreshes the native page/window attachment without reloading the document. It uses provider reflection and safely skips providers whose internal interfaces differ. Repairs wait for valid layout bounds; scroll positions use CSS coordinates across density changes. See [external-display recovery](docs/external-display-recovery.md) for the reproduction, regression checks, and verification limits. Reinstall generated apps to apply runtime changes.

Fullscreen web content (including canvases and video) uses an immersive window overlay and can fill the navigation-button area. System bars can be revealed temporarily by swiping, and exiting restores the previous bar state; the cutout option still applies. The `fullscreen` display mode also hides status and navigation bars during ordinary browsing, using [Android’s immersive mode](https://developer.android.com/develop/ui/views/layout/immersive). Other display modes show both bars until a page element enters fullscreen.

Long press a link or image to open its context menu. Link menus show the URL as their title. Links can be opened, copied, or shared, and their text can be copied separately, with an explicit option to use the system browser. Images can be opened, copied as image data, copied as an address, shared, or saved through Android’s file picker. Linked images offer both sets of actions. Image detection also handles CSS backgrounds, overlays, and open shadow DOM. HTTP(S) image transfers use the current user agent and cookies; embedded and blob images are also supported. Copy image updates the clipboard immediately without a preparation notice; its bytes load in the background, and pasting waits only if that transfer is still running. Completed copies remain readable after closing the browser. Transfers are limited to 16 MiB per image. Clipboard and shared images use temporary content-URI permissions restricted to an image cache; text selection keeps WebView’s usual behavior. The temporary browser uses the same actions with Material menus. Reinstall an existing web app to get these runtime changes.

Per-webapp **Dark mode theme color** and **Dark mode background color** are optional installer extensions, stored outside the standard manifest and included in metadata exports and backups. Empty overrides reuse the regular app colors. In dark mode they provide the toolbar/progress theme fallback and the splash/transparent-page background fallback; the current page’s own theme metadata and authored backgrounds still take precedence. Cold launches and live system-theme changes use the selected colors.

Web apps follow the system light/dark theme through native `prefers-color-scheme` support on compatible WebViews (Android 10+). CSS media queries and JavaScript `matchMedia` change listeners update in the existing document when the system theme changes, including in popups and the temporary browser. Pages keep their form values and JavaScript state; switching themes does not reload them. Websites supply their own dark styling; automatic color inversion is not enabled. Reinstall existing web apps to receive this runtime change.

Display mode controls the native UI: `browser` includes a Material toolbar; `fullscreen` hides the toolbar and system bars; `standalone`, `minimal-ui`, and the default hide the toolbar and show system bars. There is no separate toolbar option. The `browser` toolbar provides address editing, Back (long press for the back history), Forward, share, copy link, save the current page as MHTML, print, and refresh. The extra UI libraries are included only in apps using `browser` display mode. Refresh appears first in its overflow menu; the page actions are labeled **Download** and **Print**. In `browser` mode, its toolbar and the system status bar follow the current page’s first valid, matching `theme-color` meta tag, falling back to the saved app theme color, with contrasting address text, borders, navigation and menu icons. The page theme follows meta tag insertion, removal, content changes and `media` queries, including `prefers-color-scheme`, without reloading the document. If neither page nor app supplies a theme color, the toolbar and status bar use the app’s background color. A thin progress bar in the same current page theme color (falling back to the saved app theme color) overlays the top of the page while it loads and disappears when loading finishes or fails. In the other display modes, the status bar follows full-width page backgrounds, including wrapper elements and live changes; narrow buttons and cards cannot override the top color. The navigation area likewise follows only full-width backgrounds at the bottom of the page, ignores narrow buttons and cards, and adjusts button contrast; older Android versions that cannot draw dark navigation buttons use a dark backing on light pages. The native layout handles system bars, cutouts, and keyboard space, then forwards zeroed insets to WebView using [Android’s zeroing approach](https://developer.android.com/develop/ui/views/layout/webapps/understand-window-insets#the-zeroing-approach). This keeps viewport updates flowing after display and keyboard changes. This prevents WebView from reserving the same bottom space again through its visual viewport or CSS safe-area values. This policy is used throughout browsing and fullscreen transitions. A fixed-bottom-bar/keyboard fixture checks viewport geometry; the signed-in x.com layout still requires verification on the affected device. CSS `display-mode` media queries report the selected mode exactly, including `browser` and `minimal-ui`; the default is `standalone`. A supported `display_override` entry takes precedence for both native UI and media queries. A WebView compatibility script handles JavaScript `matchMedia`, inline CSS, media attributes, and dynamic stylesheets; a native interceptor translates external CSS. Current WebViews install the script at document start. Older WebViews apply it after navigation starts, so a page’s earliest scripts can still observe WebView’s browser mode. External CSS that redirects, requires native authentication, or exceeds 4 MiB falls back to WebView’s normal loader.

Manifest `shortcuts` become launcher shortcuts on first launch (API 25+), including downloaded shortcut icons. `file_handlers` register Android file-open intents for their accepted MIME types; the action receives user-granted content URIs as read-only `launchQueue` file handles with `getFile()`. `share_target` registers Android share intents and supports text/URL/title fields, GET, URL-encoded POST, and multipart POST with multiple files. Android shares containing text and links populate only the text field; a bare HTTP(S) URL populates only the URL field, falling back to text for targets without a URL mapping. Titles are kept separately. Share/file launch activities run outside the browsing task so repeated shares are processed even when the web app is already open. This follows the [Web Share Target mapping rules](https://w3c.github.io/web-share-target/#obtaining-a-sharedata) without duplicating a URL in both fields. POST shares use real form navigations, including multipart file uploads on compatible WebViews, so navigation-only service workers and normal redirects receive the content. Older WebViews that cannot assign file inputs retain a FormData fallback for file shares. Handler actions must stay within the app’s origin and manifest scope. All configured app URL scopes are registered with Android for opening links; wildcard subdomains are included. Android link filters approximate query and default-port restrictions, which are checked again by the running app. Shared files need explicit URI read grants, are limited to 16 files / 16 MiB total, and are staged in private cache. Older WebViews use a same-origin HTML bootstrap to install the file-launch queue before page scripts; current WebViews use document-start injection. No JavaScript-to-native interface is exposed.

These manifest features are also editable through **Edit full manifest JSON**. For example:

```json
{
  "file_handlers": [{"action": "/open", "accept": {"text/plain": [".txt"]}}],
  "share_target": {
    "action": "/share",
    "method": "POST",
    "enctype": "multipart/form-data",
    "params": {"title": "title", "text": "text", "url": "url",
      "files": [{"name": "files", "accept": ["text/plain", ".txt"]}]}
  },
  "shortcuts": [{"name": "New document", "url": "/new", "icons": [{"src": "/icon.svg", "sizes": "any"}]}]
}
```

Remaining manifest members, including `related_applications`, are retained and editable. The resolved web app ID is stored in both top-level metadata `id` and `manifest.id`; the internal record UUID remains separate as `key`. Web platform features such as service workers and media APIs depend on the installed system WebView and Android version. Protocol handlers are not supplied by this WebView shell.

**Passkeys:** Installed apps and the temporary browser enable WebView’s native [WebAuthn browser mode](https://developer.android.com/reference/androidx/webkit/WebSettingsCompat#WEB_AUTHENTICATION_SUPPORT_FOR_BROWSER) when supported. Android 5 compatibility is retained. Bitwarden-managed sign-in on passkeys.io has been reported working in a generated app; this confirms a functioning native credential path for that provider and site, but does not imply that every site’s authentication flow is supported. Providers have different trust policies: [Google Password Manager requires privileged-app approval](https://developer.android.com/identity/sign-in/privileged-apps) for third-party origin delegation, which is separate from Bitwarden compatibility. Passkeys remain with the credential provider and are not copied by browsing-data backups. Reinstall existing generated apps for runtime changes.

A subsequent **x.com** login succeeded on a connected Pixel 9. The live WebView trace showed a regular `navigator.credentials.get()` request from `https://x.com`, with RP ID `x.com`, one allowed credential, `userVerification: "preferred"`, and no conditional mediation. WebView returned a public-key credential, and the user confirmed successful login. No runtime change was needed for that attempt, and the cause of the earlier failure remains unknown. If it recurs, distinguish these possible compatibility issues:

- **Primary sign-in versus a second-factor security key:** [Bitwarden documents an Android restriction on non-discoverable credentials used for 2FA](https://bitwarden.com/help/auto-fill-android/#autofill-passkeys). A primary passkey login can work while the security-key step after a password does not. These are different request paths, even when the credentials live in the same vault.
- **Conditional mediation:** [Android’s WebView integration does not support `mediation: "conditional"`](https://developer.android.com/identity/sign-in/credential-manager-webview). A site relying on inline/conditional passkey suggestions can fail while a demo using an explicit credential request works. This is a compatibility candidate, not a claim that the current X flow necessarily uses it.
- **The requested relying-party ID:** passkeys are bound to their RP ID. X currently publishes reciprocal related-origin declarations at [x.com](https://x.com/.well-known/webauthn) and [twitter.com](https://twitter.com/.well-known/webauthn). A cross-domain request also depends on support in the browser and provider; editing a vault item’s website URL does not rebind the credential. Inspect the actual `rpId` before assuming a Twitter-domain credential matches the current request.

X [documents primary passkeys separately](https://help.x.com/en/managing-your-account/how-to-use-passkey); Bitwarden also tracks an [X native-Android-app compatibility report](https://github.com/bitwarden/android/issues/6587), which is not proof of the same bug in this WebView shell. To distinguish these cases, inspect the failing request’s `mediation`, `rpId`, credential transports and exception name with WebView debugging enabled; avoid publishing challenges or credential responses. The successful trace does not establish what caused the earlier failure; capture a failing attempt before attributing it to one of these possibilities. The installer does not rewrite authentication requests or bypass origin checks.

**Notifications and Push:** Web apps generated by PWA Installer use Android System WebView. Chromium does not expose the web Notifications API or Push API in Android WebView. Web notification permissions and display would need native integration in the embedding app. Background Web Push additionally needs a push transport and a browser entry point that can wake a service worker and dispatch its push event; WebView does not supply that delivery mechanism. These apps therefore cannot request web notification permission or receive Web Push messages. A page may register a service worker, but that does not add push support. See [Chromium issue 40388442](https://issues.chromium.org/issues/40388442) for the upstream request.

A proposal for optional, partial web notification support is in [notification support proposal](docs/notification-support-proposal.md). It distinguishes live-page notifications from background Web Push; neither is implemented by that proposal.

### Package naming and Android constraints

The default package name is `io.github.ulysseszh.pwainstaller.p_<hex>`, where `<hex>` is the full 40-character lowercase SHA-1 digest of the resolved manifest ID. The `p_` prefix makes the final component valid regardless of the digest's first character. A custom valid package name overrides the default; existing saved package names are retained.

### Signing and private data

The first generated APK creates a device-local RSA signing identity. In **Settings**, **Export keystore** saves the active keystore through Android’s file picker. The export preserves its original format, alias, and passwords; keep those passwords with your backup. You can import PKCS12, JKS, or BKS keystores and set the alias, store password, and private-key password. PKCS12 uses its store password for protection; JKS and BKS also support a separate key password. Settings are encrypted with AES-GCM, whose key is wrapped by an Android Keystore RSA key compatible with API 21. Keystores and signing settings stay in private storage, outside metadata exports. Changing the active signing key does not change existing web-app metadata; Android requires the original key to update an installed package.

Metadata exports include fetch headers and actual Base64 PNG icon data. Every record includes a representative `icon`, including the fallback; `icons` retains each image payload, source, format, purposes, and raster dimensions or scalable `any` size. Legacy `selectedIcon` values are removed. PNG inputs retain their original dimensions up to 1024 pixels; other raster formats retain their aspect ratio and are reduced only when needed to meet that limit. SVG inputs retain their original Base64 `sourceData`, `image/svg+xml` type, and `sizes: "any"`. A 512×512 PNG preview in `data` preserves their aspect ratio for the editor and splash; native launcher resources are rendered from the SVG at their required sizes. Imported metadata and offline APK generation use those bytes without fetching icons again; failed refreshes preserve saved icons. User-uploaded icons remain independent from manifest refreshes. When no manifest icons or uploaded icons are available, the installer discovers page `<link rel="icon">` (including `shortcut icon`) and Apple touch icons, then tries the website origin’s `/favicon.ico` if no link yields a usable image. Relative links honor the page’s final URL and `<base>` element. This also works when creating an app without a manifest. Favicons support PNG-backed ICO and common bitmap ICO formats; discovered images are stored as PNG data with the other icons. Optional discovery failures preserve existing icon data or the built-in fallback. Records are limited to 32 icons and 1.5 MiB of serialized metadata excluding filter rules. Each web app can retain up to 8 MiB of UTF-8 filter rules, stored separately in small database chunks to fit Android’s SQLite cursor windows. Exports and generated APKs retain the complete rule snapshot. Keystore credentials are excluded. Browsing-data ZIPs include cookies, site storage, and preferences, so both types of export may contain credentials. Keep them private. Metadata imports show checkboxes for choosing apps, validate the input, and commit the selection in a transaction, merging matching package names without automatically installing apps.

**Settings → Export all data / Import all data** transfers a ZIP containing all app metadata, global settings, the signing keystore and its passwords, the script/style library, cached filter lists, and browsing profiles. Unlike metadata-only exports, this archive contains signing secrets and website sessions; store it privately. Signing settings are re-encrypted with the receiving device’s Android Keystore key. Import validates payloads before changing settings and metadata. Installed apps receive their profiles when their provider permits access; otherwise profiles are retained privately for the next reinstall. Import merges metadata and does not install APKs automatically. Finish pending builds/installations before a full backup or restore. Limits are 2 GiB decompressed total, 512 MiB per profile, and 64 MiB per other entry.

A runtime provider checks the Binder caller's UID, the exact installer package, and the installer certificate hash embedded in the signed APK. A web app's own signing key can therefore differ from the installer's key. The browser runs in a separate process. Transfers stop that process and obtain an exclusive profile lock before copying data. Profiles include WebView files, preferences, and browser databases such as saved HTTP authentication. Imports validate the archive into a staging directory, reject traversal/duplicate entries/unexpected roots, limit decompressed data to 512 MiB, and replace directories with rollback on failure. The old package is retained until migration succeeds. Pending migrations survive installer process restarts and can be retried from **Continue**.

Profile transfers move Chromium's on-disk profile and can close running PWAs. Prefer transferring between apps using the same device and WebView version; profiles are not a cross-version browser interchange format. Website data protected by device hardware or origin-bound credentials may require signing in again. The installer never silently removes the old package on an installation or profile-transfer failure.

## GitHub Actions

`.github/workflows/build.yml` follows the [SunProxy build workflow](https://github.com/ulysseszh/sunproxy/blob/master/.github/workflows/build.yml). Pushes to `main` and `v*.*` tags build and check all modules, sign the release APK, upload it as the `apk` artifact, and publish it to the `apk` branch. Version tags also create a GitHub release with `app-release.apk`. The workflow pins action releases and Android command-line tools verified on October 20, 2026. JDK 21 is retained for compatibility with Gradle 8.13.

Configure repository Actions secrets `SIGNING_KEY_BASE64`, `ALIAS`, `KEY_STORE_PASSWORD`, and `KEY_PASSWORD`. The first is the Base64-encoded installer signing keystore; retain the same certificate for future installer updates. These CI credentials sign PWA Installer itself; generated web apps use the keystore configured on the device. The publishing job needs permission to write repository contents. Store descriptions are in `metadata/en-US/` and `metadata/zh-CN/`.
